# Daily Log Sync

这个 skill 同时支持两种触发方式：
- slash command：`/daily-log-sync`
- 自然语言：如“总结今天的分析和问题”“更新今天的日志”“整理今天的排查结论”

当用户输入 `/daily-log-sync`，或表达上述近似意图时，使用这个 skill。

这个 skill 的目标不是生成浅层日报，也不是只罗列改动文件，而是生成简洁、可复盘、不过度展开的工程分析总结。

## 适用场景
- 需要通过 `/daily-log-sync` 快速整理当天工作，而不是每次手写完整提示词
- 需要直接发一句自然语言也能完成同样的日志整理
- 需要把当前会话中的分析、排查、结论和修改结果整理进当天日志
- 需要在已有当日日志基础上继续增量更新，而不是新建重复文档
- 需要把多个表面问题梳理成更深层的共性结论
- 需要把未完成问题统一维护到文末“待后续完善问题”
- 需要避免因为多窗口、上下文压缩、会话切换而导致日志风格不一致

## 核心目标
1. 同一天只维护一份主日志
2. 已有日志优先读取并增量更新，而不是重复新建
3. 不只写“改了什么”，而要尽量写清：
   - 问题现象
   - 初步排查中一度怀疑的方向
   - 最终确认的正确原因 / 最终正确根因
   - 为什么最终采用当前修改方案
   - 最终修改结果
4. 当存在多个问题时，不只逐条记录，还要尽量在文末总结它们共同指向的设计原则或根因模式
5. 未完成问题统一维护在文末“待后续完善问题”
6. 已完成的旧待办要同步关闭，不允许正文和文末状态冲突

## 强制写作要求
1. 如果用户提供的信息足够，正文应尽量接近以下表达层次：
   - 本次涉及组件 / 文件 / 模块
   - 问题 1 / 问题 2 / 问题 3 ...
   - 每个问题下继续拆分：
     - 问题现象
     - 初步排查中一度怀疑的方向
     - 最终正确结论
     - 为什么会这样
     - 为什么最终采用当前修改方案
     - 最终结果
     - 本问题的最终正确结论摘要
   - 当天最终修改结果汇总
   - 今天的简要结论
   - 待后续完善问题（如仍存在未完成事项，且必须始终放在文末）
2. “中途怀疑”与“最终正确结论”必须明确分开，不能混写。
3. 如果排查过程中排除了若干看似合理的方向，应尽量说明“为什么这些方向不是最终根因”。
4. 只有同一交互、同一需求、同一条问题链路中的内容，才应合并成一个问题；如果是同一天内的多个独立问题、多个独立提问或多个独立修改点，必须拆分为多个问题章节，不能因为都发生在今天就合并成一个问题。
5. 如果多个问题本质上属于同一类根因，应在总结部分明确指出，但仍要先判断它们是否属于彼此独立的问题；不要把多个独立问题强行合并成一个大问题。
6. 不要只写结果，要尽量让后续回看的人能直接理解：
   - 当时为什么会误判
   - 最终为什么确认是当前结论
   - 为什么最终方案比其他候选方案更合理

## 执行要求
1. 先确认目标日期；未指定时默认按当天处理。
2. 先确定日志目录：优先使用用户明确指定的目录；如果用户没有指定，则默认使用当前项目根目录。
3. 在目标目录中先查找该日期已有日志；若存在，先读取旧日志再更新。
4. 如果目标目录中不存在该日期日志，则在同一目标目录创建当天新日志；除非用户明确要求写入某个子目录，否则不要自行把日志放到子目录中。
5. 无论用户是输入 `/daily-log-sync`，还是直接用自然语言请求总结/更新日志，默认目标都是直接维护对应日志文件，而不是在上下文中完整输出正文。
6. 如果用户只输入 `/daily-log-sync` 这类短命令，默认基于当前会话整理今天的分析、问题、最终结论与未完成事项，不要先反问。
7. 如果用户只发自然语言请求，也按同一套日志维护流程执行，不要因为没有 slash command 就降低优先级或改走别的总结风格。
8. 历史摘要或上下文压缩总结只能作为辅助输入，不能直接当正式正文。
9. 优先把新信息补到已有问题章节，而不是创建重复章节。
10. 如果当前修改涉及多个组件、多个文件或多处逻辑，尽量单独列出“本次涉及组件 / 文件”，方便后续回看。
11. 如果本轮工作只有一个核心交互或一个核心问题，应优先合并记录，不要机械拆成多个问题章节。
12. 写当天日志时，只能记录本次会话中当天实际分析、排查、修改或确认过的问题；已经在更早会话中解决、且本次没有继续处理的问题，不应因为“相关”或“同属一个模块”就再次写入今天日志。
13. 如果本轮出现多个独立提问或多个独立修改任务，即使都属于同一页面或同一模块，也应优先拆成多个问题章节，除非它们明确属于同一条连续问题链路。
14. 如果检测到已有日志中存在“待后续完善问题”，必须结合旧日志内容与当前上下文重新判断这些问题是否仍未解决；如果已经解决，必须把相关结论或修复结果补回正文对应章节或结果汇总，并同步从“待后续完善问题”中删除。
15. 只有当前上下文与现有日志都表明问题仍未解决时，才继续保留该待办；如果用户已手动删除某项待办，且当前日志中已不存在该项，就不要自行补回。
16. 如果本次更新完成后已没有任何未完成事项，应直接删除“待后续完善问题”整个章节，而不是为了形式保留空标题或继续写旧问题。
17. “待后续完善问题”如果存在，必须始终放在整篇文档最后一个正式章节；不要把“今天的简要结论”或其他总结章节放在它后面。
18. 完成日志整理后，应优先使用工具直接写入或更新目标 markdown 文件；只有在用户明确要求“先预览、不落盘”时，才只在上下文展示正文。
19. 如果日志已经落盘，回复中只需简要说明：写入/更新了哪个文件、采用了什么目录、是否有未完成事项；不要在上下文再次完整粘贴整篇日志。
20. 如果写入、更新、读取旧日志或定位目标目录失败，默认不要退回成长篇正文输出；应先用简短说明告知失败点、当前阻塞原因以及下一步需要用户确认或补充的信息。

## 输出要求
- 默认输出应以“执行结果说明”为主，而不是完整 markdown 正文
- 正式日志内容应优先写入目标文件，而不是在聊天窗口长篇展开
- 风格应工程化、可复盘、层次清晰
- 不要退化成文件列表、命令流水账或浅层总结
- 不要只像聊天纪要，要像一份以后还能直接指导继续修改的分析文档
- 当用户仅输入 `/daily-log-sync` 或等价短指令时，也应直接按上述规则完成当天日志维护，而不是反问用户是否要总结
- 当用户仅用自然语言提出“总结今天分析和问题”“更新今天日志”等请求时，也应直接命中这套规则，而不是退化为普通聊天式总结
- 当日志已成功写入文件后，不要再把完整正文重复输出到上下文，以减少上下文与 token 消耗
