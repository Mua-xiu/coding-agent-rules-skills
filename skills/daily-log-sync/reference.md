# Reference

## 一、合并规则
- 同一日期默认只维护一份主日志
- 已有当日日志存在时，优先更新旧文档
- 同一问题优先合并进原章节，不重复创建近似章节
- 历史摘要只能辅助判断，不直接粘贴成正式正文
- 已有文档如果已经形成较完整结构，优先在原结构基础上补充，而不是粗暴重写

## 二、日志目录规则
- 优先使用用户明确指定的日志目录
- 如果用户没有指定目录，则默认使用当前项目根目录
- 应先在目标目录检查当天是否已有主日志；若已有，则继续增量更新该文档
- 若目标目录下不存在当天日志，则在同一目标目录创建当天新日志
- 除非用户明确要求写入某个子目录，否则不要自行把日志放到子目录中
- 默认目标是直接维护目标目录中的日志文件，而不是把整篇正文先输出在上下文中
- 只记录当前会话中当天实际分析、排查、修改或确认过的问题；不要把更早会话里已经解决、且本次没有继续处理的问题重新写进今天日志

## 三、落盘与回复规则
- 无论通过 slash command 还是自然语言触发，默认都应直接写入或更新目标 markdown 文件
- 只有当用户明确要求“先预览”“先不要写文件”“只给我看看草稿”时，才只在上下文输出正文
- 日志已经成功写入后，回复中只需简要说明：目标文件路径、本次是新建还是更新、是否仍有待后续完善问题
- 不要在回复中重复粘贴整篇正式日志正文，以减少上下文占用和 token 消耗
- 如果因为缺少必要信息暂时无法安全落盘，也应优先用简短说明指出阻塞点，而不是先输出长篇草稿
- 如果写入、更新、读取旧日志或定位目标目录失败，默认不要退回成长篇正文输出；应优先给出简短失败说明和下一步所需信息

## 四、正文最低要求
每个重要问题尽量覆盖：
1. 问题现象
2. 排查分析
3. 最终正确分析 / 最终正确根因
4. 为什么最终采用当前修改方案
5. 修改结果 / 当前状态
6. 本问题的最终正确结论摘要

按实际过程补充：
- 如果排查过程中确实出现过误判方向、候选方向或看似合理但被排除的方向，应单独写“初步排查中一度怀疑的方向”
- 如果本次处理存在影响面、兼容性、历史逻辑、回滚成本或其他风险取舍，应单独写“风险点与方案取舍”
- 如果只是常规业务处理、简单配置调整或没有明确误判过程，不要为了凑结构强行生成“怀疑方向”标题

说明：
- 不要求每个问题都机械拆成很多小标题，能在一个问题章节内顺畅说明即可
- 删除可选小节后，正式日志中的小节编号必须按实际保留内容连续重排，避免出现跳号
- 只有同一交互、同一需求、同一条问题链路中的内容，才应优先合并成一个问题
- 如果是同一天内的多个独立提问、多个独立修改点或多个独立问题，即使它们都发生在同一个页面或模块中，也必须拆分成多个问题章节
- 不要为了凑结构拆成多个问题，但也不要因为都发生在今天就强行合并成一个大问题

## 五、比普通总结更高的要求
高质量日志不应只停留在“记录发生了什么”，还应根据实际过程尽量回答：
- 排查分析是如何收束到最终结论的
- 如果一开始发生过误判，为什么会误判
- 如果某些看似合理的方向被排除，为什么它们不是最终根因
- 如果存在候选方案或风险点，为什么当前方案比其他候选方案更稳妥
- 多个问题之间是否有共同根因、共同设计原则或共同风险点

也就是说，日志应尽量呈现：
- 表面现象
- 排查分析路径
- 最终确认路径
- 必要时补充误判路径、风险点和方案取舍
- 设计原则收束

## 六、推荐结构深度
如果信息足够，优先接近以下层次：
1. 本次涉及组件 / 文件 / 模块
2. 问题 1 / 问题 2 / 问题 3 ...
3. 每个问题下包含：
   - 问题现象
   - 排查分析
   - 最终正确结论
   - 为什么会这样
   - 为什么最终采用当前修改方案
   - 最终结果
   - 本问题的最终正确结论摘要
4. 如果实际存在误判方向、候选方向、被排除的方向或风险取舍，应在对应问题下增加相关小节；如果不存在，不要强行添加
5. 当天最终修改结果汇总
6. 今天的简要结论
7. 待后续完善问题（如果存在，必须始终放在文末）

## 七、严禁退化成以下形式
- 只有文件列表
- 只有命令流水账
- 只有“已完成/未完成”口号
- 只写结果，不写原因
- 只写修改点，不写业务背景和技术背景
- 把多个本质相关的问题写成彼此无关的碎片

## 八、涉及文件 / 组件的处理规则
- 如果这轮工作明确涉及多个组件、文件或模块，建议单独列出“本次涉及组件”或“本次涉及文件”
- 列出文件不是为了凑清单，而是为了让后续回看的人快速定位现场
- 只有在这些文件确实参与本轮问题链路时才列出，避免无意义堆砌

## 九、待后续完善问题规则
- 所有未完成问题统一放在文末
- 每条至少写明：问题名称、当前状态、未完成原因、下次优先关注点
- 如果旧待办已经完成，必须把关键结论补回正文，并同步关闭待办
- 不允许正文写“已完成”，文末却还保留旧未完成项
- 检测到已有日志时，必须重新检查旧“待后续完善问题”中的每一项是否已在当前上下文中解决
- 如果某项待办已经解决，应把相关分析结论、修复结果或最终状态补回正文对应位置，并从“待后续完善问题”中删除
- 如果用户已手动删除某项待办，且当前日志中已不存在该项，不要自行恢复该待办
- 如果本次更新后不存在任何未完成事项，应直接删除整个“待后续完善问题”章节，而不是保留空标题或用“无”占位
- 如果“待后续完善问题”章节存在，它必须始终是全文最后一个正式章节

## 十、风格要求
- 中文优先
- 工程化、可复盘
- 一眼能看到最终正确结论
- 一眼能看到为什么最终这样改
- 一眼能看到这轮修改最重要的原则性收获
