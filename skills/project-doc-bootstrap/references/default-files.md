# Project Doc Bootstrap 默认文件模板

本文件提供生成基础协作文档时的技术栈中立模板。模板中的项目名称、目录、命令、技术栈和规则目录都必须按目标项目事实改写；无法确认的信息不要编造，可以标记为“待确认”。示例中的前端、后端、Agent、CLI、数据和基础设施术语都只是候选项，不代表默认生成要求。

## 根入口：AGENTS.md

```markdown
# 项目协作入口

本文件维护本项目专属的 Agent 渐进式披露规则。进入项目后先读本文件，再按当前任务命中的索引读取 `AGENTSDOC/rules/` 下的细则；不命中的规则不读，避免无关上下文干扰。

## 元规则（每次任务必读）

- 使用中文回复用户；代码注释优先使用中文，除非项目已有明确英文注释规范。
- 默认采用改动最小且可靠的方案；如果最小方案存在明显 bug、性能、安全或维护隐患，应说明风险并选择更稳妥方案。
- 围绕用户明确范围执行；影响实现方向、改动范围或验收标准的不确定点，需要先确认。
- 不盲目添加与当前任务无关的功能、创新设计、目录重构或未来扩展。
- 新增、删除、重命名或调整 `AGENTSDOC/rules/` 下正式规则时，必须同步更新本文件的规则索引。
- 过程文档、计划、复盘、基线和参考稿放入 `AGENTSDOC/plans/<主题>/`，不要散落到仓库根目录或业务代码目录。

## 全局规则索引

- 了解项目结构、技术栈、运行测试命令、目录职责和交付方式时，读取 `AGENTSDOC/rules/global/project.md`。
- 判断任务边界、是否需要确认、是否扩大范围时，读取 `AGENTSDOC/rules/global/task-boundary.md`。
- 编写或修改函数、类、服务、组件、Agent、任务、配置、关键变量或旧逻辑注释时，读取 `AGENTSDOC/rules/global/comments.md`。
- 新增计划、复盘、提案、规则、基线或其它过程文档时，读取 `AGENTSDOC/rules/global/doc-archive.md`。
- 新建、迁移、重构或调整业务模块目录时，读取 `AGENTSDOC/rules/global/module-structure.md`。

## 模块规则索引

- `<按项目补充触发条件>` → `AGENTSDOC/rules/<模块>/...`

## 阅读路径

1. 进入项目后先读取本文件，元规则全部生效。
2. 根据当前任务命中上方索引，再读取对应规则文件。
3. 规则文件只负责说明读取顺序、硬性约束和定位方式；详细 API、数据模型、组件契约、协议、部署设计等按规则中的路径继续按需读取。
4. 若发现规则与实际代码、运行结果、外部契约或构建配置不一致，以可验证事实为准；需要长期生效时同步更新规则文档。
```

## 可选双入口：CLAUDE.md

如果项目同时服务 Claude Code，建议让 `CLAUDE.md` 与 `AGENTS.md` 保持等价内容，而不是只写一句“见 AGENTS.md”。不同工具不一定会继续追踪跳转链接，完整双入口能减少 AI 读取到不同规则的概率。

## `AGENTSDOC/rules/global/task-boundary.md`

```markdown
# 任务边界规则

## 适用场景

判断是否需要扩大范围、补充需求、修改计划、处理风险或确认不确定点时读取。

## 硬规则

- 优先围绕用户明确给出的任务范围执行，不盲目添加无关功能或重构。
- 初步分析后若存在影响实现方向、改动范围或验收标准的不确定点，应先确认。
- 发现提示词遗漏的重大漏洞、危险操作或明显会影响正确性的风险时，应说明风险并询问是否补充修复。
- 推荐方案默认从改动最小的有效方案开始；若最小方案有明显隐患，应推荐更稳妥方案。
- 为未来扩展预留设计前，先说明价值、成本和影响范围，并得到用户同意。
- 不因计划文档缺失而阻塞；按正式规则执行，必要时生成本地计划。

## 详细说明

Agent 的执行标准是“有效、可靠、范围清晰”。不要为了显得完整而创造需求，也不要为了追求最小改动保留明显问题。
```

## `AGENTSDOC/rules/global/comments.md`

```markdown
# 注释规则

## 适用场景

编写或修改函数、类、服务、控制器、组件、Agent、工作流、任务、脚本、配置、类型和旧逻辑时读取。

## 硬规则

- 代码注释优先使用中文，说明职责、业务原因、输入输出、边界条件或保留意图。
- 函数、类、服务、组件、Agent、任务和模块的关键职责应有简短说明。
- 关键变量、常量、配置项、枚举、映射表、阈值和状态标记应说明含义或来源。
- 项目存在 HTML、Vue template、JSX 等界面结构时，主要区块之间应添加名称注释，方便快速定位。
- 对隐藏、停用、兼容历史逻辑、绕开旧服务、修复旧模块问题等改动，应说明原因和恢复意图。
- 修复 bug、处理旧模块或调整既有逻辑时，必要注释可补充日期；常规新代码不需要日期。
- 不为一眼能看懂的普通赋值、简单模板或重复代码添加冗余注释。

## 详细说明

注释重点是“为什么存在”和“负责什么”，不要只写“开始函数”“重置函数”这类无法帮助复盘的描述。
```

## `AGENTSDOC/rules/global/doc-archive.md`

```markdown
# 文档归档规则

## 适用场景

新增计划、复盘、提案、规则、基线、参考稿、过程说明或调整文档治理结构时读取。

## 硬规则

- 正式长期规则放入 `AGENTSDOC/rules/`，按 `global`、业务模块或职责目录归档。
- 过程文档放入 `AGENTSDOC/plans/`，该目录作为本地工作台，默认不入库。
- `AGENTSDOC/README.md` 不作为索引入口；索引职责统一由根目录 `AGENTS.md`，以及存在时的 `CLAUDE.md` 承担。
- 新增、删除、重命名或调整 `AGENTSDOC/rules/` 下规则时，必须同步更新根入口文档。
- 新增过程文档时按主题放入 `AGENTSDOC/plans/<主题>/`，文件名使用语义化短横线命名，如 `api-cleanup-plan.md`。
- 不要把临时计划、分析稿、参考稿散落到仓库根目录、业务代码目录或 `public/`。
- 入库文档不要链接到 `AGENTSDOC/plans/` 下具体文件，避免克隆后出现本地过程文档死链。

## 详细说明

规则文档用于长期约束，过程文档用于阶段性分析和复盘。若某个过程文档结论需要长期生效，应提炼成 `AGENTSDOC/rules/` 下的正式规则，并同步更新根入口索引。
```

## `AGENTSDOC/rules/global/module-structure.md`

```markdown
# 模块结构规则

## 适用场景

新建、迁移、重构或调整业务模块目录时读取。

## 硬规则

- 业务模块默认按项目既有目录组织；如果项目已有模块命名和分层方式，优先沿用。
- 模块文档目录名应尽量与代码模块名一致，方便从规则、计划回到真实代码。
- 模块内部代码、数据模型、配置、测试、脚本和资源优先就近维护；只有真正跨模块复用时才上提到公共层。
- 不为“看起来统一”强制创建空目录或空文件；目录随真实职责、契约、数据、测试或资源需求出现。
- 调整代码模块名时，同步检查 `AGENTSDOC/rules/` 与 `AGENTSDOC/plans/` 中对应目录名是否需要调整。
- 如果用户只要求局部功能修复，不借机重排模块结构。

## 详细说明

本文件只规定模块组织原则。具体 API、数据模型、服务边界、Agent 工作流、组件系统、部署或基础设施规则，应按项目实际另建规则文件并在根入口索引。
```
