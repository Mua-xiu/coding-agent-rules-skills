# 1 - 新多模型讨论 Skill 执行计划

## 前置条件

必须先完成 `0-profile-settings-foundation.md`，并确认：

- `claude-orchestrator` 已支持 `profile-settings` 默认模式。
- `claude --settings ~/.claude/profiles/<profile>/settings.json` 已验证可用。
- `health.json`、TTL、失败重测和 `--ping` 能稳定运行。
- 共享脚本读写协议已经在文档中明确。

未满足以上条件前，不开始实现本阶段。

## 目标

开发新的多模型讨论 skill，让多个可用 Claude profile 围绕用户问题进行结构化讨论、互评和修正，最后由 Codex 进行最终裁决，输出问题等级和可执行建议。

本 skill 的目标不是让模型投票决定结论，而是让多个模型暴露不同视角、风险和执行路径，再由 Codex 统一判断。

## 核心机制

### 结构化讨论

至少包含以下阶段：

1. 独立首轮回答：每个模型基于同一问题独立给出观点，避免互相带偏。
2. 互评与质疑：每个模型读取其他模型观点后，指出问题、风险和遗漏。
3. 修正建议：每个模型根据质疑修正自己的建议。
4. Codex 裁决：Codex 读取讨论记录，判断最佳方案、问题等级和下一步动作。

### 会话与消息记录

讨论记录的主要目的，是让不同模型账号在切换后能接上前序账号的输出结论、质疑和修正意见。

需要保留：

- 每个参与者的 `session-id` 或等价会话标识。
- 每轮消息顺序。
- 控制器状态。
- 面向 Codex 审查的 transcript。

讨论记录不默认作为目标项目长期归档，不一开始设计复杂项目目录。落盘位置先由新 skill 自身运行目录管理；后续如果用户明确需要长期归档，再单独设计。

### 直接消息路由

如实现交互式讨论，需要支持模型间定向消息：

- question
- challenge
- answer
- support

必须设置 `--max-directed-turns` 或等价上限，防止模型互相追问导致无限循环。

## 参与者选择

- 默认从 `~/.claude/profiles/` 中读取健康可用的 profile。
- 支持 `--profiles architect,implementer` 指定参与者。
- 支持 `--profiles all`。
- 支持 `--max-participants <n>` 截断参与者数量。
- 跳过 `health.json.status=down` 且重测失败的 profile，并在结果中告知用户。
- 不继承旧 `api-profiles.json`。

## Codex 裁决规则

Codex 必须读取讨论记录后裁决，不允许模型投票替代结论。

裁决时判断：

- 哪些观点有充分证据。
- 哪些观点只是猜测或过度设计。
- 哪些问题会阻塞任务执行。
- 哪些问题只是优化项或未来扩展项。
- 哪些事项需要用户补充确认。

## P0-P4 问题等级

所有等级的问题都必须告知用户，不能因为问题较小就隐藏。

- `P0`：高危或阻塞问题，不解决不能继续。
- `P1`：正式执行前必须处理的问题，否则会明显影响正确性、安全性或主要目标。
- `P2`：应该处理的问题，会影响质量、维护性或边界情况，但不阻塞主线。
- `P3`：可延后优化项。
- `P4`：未来扩展或体验增强建议。

模型可以提出分级建议，但最终等级由 Codex 根据任务目标、证据和风险统一判断。

## 计划文档生成规则

最终计划文档不是无条件生成。

- 如果存在 `P0` / `P1` 或任务边界仍不明确，Codex 应先把所有问题等级、影响和建议处理方式告知用户，并询问是否需要补充、修正或生成计划文档。
- 如果只存在 `P2` / `P3` / `P4`，且任务边界、执行顺序和验收方式明确，可以先生成计划文档草案，同时列出这些问题及优先级，询问用户是否需要先调整计划再执行。
- 如果讨论结论表明任务可以直接完成，且无需长期留存计划文档，Codex 可以直接说明执行方案并等待用户确认。

计划文档只承载 Codex 裁决后的可执行方案，不粘贴完整讨论记录。

## 输出建议

最终回复至少包含：

- 最终建议。
- 关键依据。
- P0-P4 问题列表。
- 是否建议生成计划文档。
- 如果已生成计划文档，给出路径。
- 需要用户确认的下一步。

## 安全规则

- 不把 API key、token、profile 快照写入 prompt、transcript、计划文档或最终回复。
- 默认禁止模型直接编辑文件。
- 只有用户明确要求工具调查或实现时，才允许模型读取或修改文件。
- 模型声称看过本地文件时，Codex 必须自行核验。
- 失败的模型调用必须记录并告知用户，不能静默忽略。

## 验收标准

- 至少能完成一次 2 个 profile 的结构化讨论。
- 每个参与者首轮回答互相独立。
- 能生成可供 Codex 审查的 transcript。
- 能记录失败参与者并继续处理可用参与者。
- Codex 最终输出包含 P0-P4 分级。
- 不使用多数票替代 Codex 裁决。
- 默认不修改目标项目文件。

## 暂不处理

- 不做复杂长期归档目录体系。
- 不继承旧 V1 batch 模式，除非后续确实需要快速一次性比较。
- 不使用 `api-profiles.json`。
- 不生成临时 settings 文件。
